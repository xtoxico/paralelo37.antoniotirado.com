Los tres nombres

FIDO2 Fast Identity Online 2.0. El paraguas: el estándar abierto de autenticación sin contraseñas.
WebAuthn La API del W3C que tu página web llama. Es JavaScript: navigator.credentials.
CTAP2 Client To Authenticator Protocol. Cómo el navegador habla con el aparato que guarda las claves.

FIDO2 = WebAuthn + CTAP2

Los tres actores

Relying Party Tu servidor. El que confía en la firma. Express.js
Client Navegador + sistema operativo. Traduce WebAuthn ⇄ CTAP2. Chrome
Authenticator Donde vive la clave privada. Nunca sale de ahí. Touch ID, YubiKey, Pico
Dibujar el triángulo en la pizarra si la hay. Insistir: tu servidor NUNCA habla con el autenticador. Siempre a través del navegador.

Ventajas, en cuatro golpes

Sin contraseñas

Criptografía sin dolor

Todo lo que hace falta entender cabe en cinco líneas.

El par de claves


// 1. El autenticador crea un par ÚNICO para este sitio
const { privateKey, publicKey } = generateKeyPair();

// 2. La privada NUNCA sale del dispositivo
//    (la pública sí: se la mandamos al servidor)
servidor.guardar(usuario, publicKey);

// 3. Para entrar, el autenticador FIRMA un reto
const firma = privateKey.sign(reto);

// 4. El servidor comprueba la firma con la clave pública
const valida = publicKey.verify(reto, firma);
Analogía: la clave pública es un candado abierto que reparto a todo el mundo; la privada es la única llave que lo cierra. Si se filtra mi base de datos, el atacante se lleva una colección de candados abiertos.

¿Por qué esto mata el phishing?

Cada credencial se crea para un rpID concreto: tubanco.es

El navegador comprueba el dominio antes de pedir la firma.

En tubanc0.es el autenticador ni siquiera se despierta.

No es que el usuario no se equivoque: es que no puede equivocarse.

Y el reto (challenge)

  • El servidor genera un valor aleatorio y nuevo en cada intento
  • La firma solo vale para ese reto
  • Capturar el tráfico de ayer no sirve para entrar hoy

Esto es lo que se llama protección contra replay.

Flujo de REGISTRO

  1. El usuario escribe su nombre
  2. El servidor genera un reto y las opciones
  3. El navegador llama a navigator.credentials.create()
  4. El autenticador pide huella/PIN y genera el par de claves
  5. El navegador devuelve la clave pública firmada
  6. El servidor verifica y la almacena

Flujo de AUTENTICACIÓN

  1. El usuario escribe su nombre (o ni eso, con passkeys)
  2. El servidor genera un reto nuevo + los IDs válidos
  3. El navegador llama a navigator.credentials.get()
  4. El autenticador firma el reto con la clave privada
  5. El navegador envía la assertion: firma + datos
  6. El servidor verifica la firma con la clave pública
Insistir en la simetría: mismos dos viajes, cambia lo que hace el autenticador en medio. Crear vs firmar.

La configuración: tres constantes


const rpName = 'Taller FIDO2 — Paralelo 37';  // Lo que ve el usuario
const rpID   = 'localhost';                    // El dominio que ata la credencial
const origin = 'http://localhost:4200';        // Desde dónde aceptamos peticiones

Si rpID y origin no encajan, nada funciona. Es el error número uno.

Endpoint 1 · /auth/register/begin


const opciones = await generateRegistrationOptions({
  rpName, rpID, userName: usuario,
  attestationType: 'none',
  excludeCredentials: registro.credenciales.map(
    (c) => ({ id: c.id, transports: c.transports })),
  authenticatorSelection: {
    residentKey: 'preferred',
    userVerification: 'preferred',
  },
});

registro.reto = opciones.challenge;  // Lo guardamos para el paso 2
respuesta.json(opciones);

Endpoint 2 · /auth/register/complete


const { verified, registrationInfo } = await verifyRegistrationResponse({
  response: credencialNueva,
  expectedChallenge: registro.reto,  // ¿firmó ESTE reto?
  expectedOrigin: origin,            // ¿vino de NUESTRA web?
  expectedRPID: rpID,                // ¿es para nuestro dominio?
  requireUserVerification: false,
});

const { credential } = registrationInfo;
registro.credenciales.push({
  id: credential.id,
  publicKey: Buffer.from(credential.publicKey).toString('base64url'),
  counter: credential.counter,
});

Fíjate en lo que guardamos: una clave pública y un número.

Endpoints 3 y 4 · el login


// begin: un reto NUEVO y qué credenciales valen
const opciones = await generateAuthenticationOptions({
  rpID,
  allowCredentials: registro.credenciales.map(
    (c) => ({ id: c.id, transports: c.transports })),
});

// complete: verificar la firma con la clave pública guardada
const { verified, authenticationInfo } = await verifyAuthenticationResponse({
  response: firma,
  expectedChallenge: registro.reto,
  expectedOrigin: origin,
  expectedRPID: rpID,
  credential: { id, publicKey, counter, transports },
});

credencial.counter = authenticationInfo.newCounter;  // anti-replay

El servicio: registrar


async registrar(usuario: string): Promise<void> {
  // 1) Pedimos el reto al backend
  const opciones = await this.post<...>('register/begin', { usuario });

  // 2) El navegador abre el diálogo nativo y nace el par de claves
  const credencial = await startRegistration({ optionsJSON: opciones });

  // 3) Mandamos al servidor solo la clave pública firmada
  await this.post('register/complete', { usuario, credencial });
}

El servicio: entrar


async entrar(usuario: string): Promise<void> {
  const opciones = await this.post<...>('login/begin', { usuario });
  const credencial = await startAuthentication({ optionsJSON: opciones });
  await this.post('login/complete', { usuario, credencial });
  this.usuario.set(usuario);
}

Exactamente la misma forma. Cambia create por get.

¿Por qué RP2350 y no RP2040?

RP2350 / ESP32-S3

Secure Boot y Secure Lock.

Clave maestra en memoria OTP que cifra las credenciales.

La flash no se puede volcar.

RP2040

Sin esa protección.

Quien te robe la placa puede volcar la flash y sacar las claves privadas.

Entonces, ¿para qué pagar una YubiKey?

La matemática es idéntica.
Lo que compras es que nadie pueda abrir la caja.

Elemento seguro certificado, resistencia física a ataques, cadena de attestation reconocida.

Y aquí conecta con tu backend


attestationType: 'none'    // nuestra llave casera funciona
attestationType: 'direct'  // el servidor puede exigir certificado de fabricante
  • Pico FIDO hace self-attestation: no tiene cadena de fabricante reconocida
  • Un banco que valide el AAGUID contra los metadatos de la FIDO Alliance la rechazará

Ese parámetro que llevas media hora copiando sin pensar: para esto sirve.

Bonus: la semilla de 24 palabras

Pico FIDO permite respaldar el dispositivo y restaurarlo en otra placa.

Las llaves comerciales no dejan hacer esto, por diseño.

Allí la única estrategia es registrar dos llaves por cuenta.
